# Harvest: build journal

Dates: 2026-10-19 to 2026-10-20.
Spec: `docs/superpowers/specs/2026-10-19-harvest-design.md` (§15 lists every ruling).
Plan: `docs/superpowers/plans/2026-10-19-harvest.md`.

## Goal

Bring the `find-all-images` work into Pixel Magic: find real photos on external drives and NAS shares and feed them to the drop zone, so the vault keeps each photo once.

- The user picks drives or folders on a local page; nothing scans on a schedule, and a source done before is rescanned only when picked again.
- Sources are only ever read.
- Copying is paced (disk ≤ 80 %, backlog ≤ 20,000) and survives reboots, crashes and unplugs.

## How it was built

- **Design.** Brainstormed with the user: a local web page, drive plus folder selection, possible photos reviewed with thumbnails, the harvester started at login, NAS-Backup re-harvested from the NAS.
- **Shape.** One native Mac process (Temporal worker on queue `harvest` plus an HTTP server on 127.0.0.1:3020), because only the host sees `/Volumes` and `diskutil`. The pipeline containers are unchanged.
- **Process.** Subagent-driven development over 13 tasks, each with a task review and fix rounds; then a whole-branch review, one fix wave and its re-review. About 45 rulings were made without stopping, each logged with its cost if wrong.

## What the reviews found

- **Lost photos by name.** Non-UTF-8 and NFD names (macOS writes NFD onto exFAT and SMB) would have been marked failed or "gone". Sources are now read by their on-disk bytes.
- **Unplug mid-folder.** A drive pulled part-way through a folder would have recorded that folder as done. The scan now notices the mount is gone and commits nothing for it.
- **Overwrite race.** `rename` can replace a file; publishing now uses link-then-unlink, which never does.
- **Time precision.** File times can't be set to the nanosecond, so the copy's real time is recorded and used to link it to the pipeline.
- **Approvals.** Approving a few possible photos would have scanned, then sent, whole folders. A send-only run now sends exactly the approved files.
- **Duplicates.** A changed file of the same size, or one on another volume at the same mount point, could have been taken as a duplicate. Candidates are now checked against their current bytes, and only within the run.
- **Permissions.** Under launchd, macOS may deny `node` access to removable and network volumes; such a folder would have been marked harvested. The run now pauses with "permission denied".
- **Long waits.** A multi-day unplug during a scan would have hit Temporal's history limit and wedged the queue. The scan loop now continues as new.
- **Scale.** Paging, indexes and a larger libuv pool keep a 600k-item ledger and a hung SMB share from slowing everything.

## Results

- **Tests.** 1,017 unit and workflow tests pass; coverage 95.5 % of lines and 89.7 % of branches. The end-to-end tier harvests a cloned corpus with every photo twice: 86 sent, 86 duplicates skipped, junk never sent, the source untouched, and a second harvest sends nothing.
- **Dry runs on real data** (read-only, nothing sent) matched `find-all-images` exactly:
  - NAS-Backup: 17,402 photos (56 GB), 337 possible photos, 0 errors, 10 minutes.
  - Expansion: 622,804 photos (1.89 TB), 7,994 possible photos, 0 errors, 22 minutes.

## Open items

- Real harvests have not run yet. They need the login agent installed and `node` granted access to removable and network volumes; both are the user's call.
- Minor items deferred by the reviews are listed in the ledger summary given to the user.
